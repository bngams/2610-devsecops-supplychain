Partie 1

Cadre, référentiels et acteurs

La sécurité applicative ne vit pas seule : elle répond à des obligations (conformité), s'inscrit dans une organisation (rôles) et se nourrit d'une veille continue.

Conformité → certification

Référentiels

  • ISO 27001 : SMSI, socle générique (RGPD, NIS2 s'y adossent).
  • NIS2 : directive UE, entités « essentielles / importantes », obligations de gestion des risques et de notification d'incident.
  • DORA : résilience opérationnelle numérique du secteur financier (ACPR), inclut le risque lié aux prestataires TIC.
  • SOC 2 : rapport d'audit (Trust Services Criteria) très demandé par les clients SaaS.
  • Sectoriels : plateformes agréées facturation électronique, aviation, santé (ANS/ARS, programme CaRE).
  • RGPD : minimisation, chiffrement, pseudonymisation, données en dev/preprod.
Organismes FR

ANSSI & CERT-FR

  • ANSSI (cyber.gouv.fr) : guides et recommandations (ex. déploiement de conteneurs Docker, parcours de sécurisation sur messervices.cyber.gouv.fr).
  • CERT-FR : alertes, avis de vulnérabilités, bulletins (veille passive par abonnement).
  • BPI / financements, diagnostics cyber.
Dans l'entreprise

Rôles et structures

DSI
pilote le SI, arbitre budgets et priorités
RSSI
politique de sécurité (PSSI), risques, conformité, sensibilisation
SOC
supervision 24/7, SIEM, détection
CERT/CSIRT
réponse à incident, coordination
VOC
gestion du cycle de vie des vulnérabilités (priorisation, remédiation)
Dev / Ops
appliquent en continu : c'est l'objet de la partie 4
Veille

Passive et active

  • Passive : abonnements CERT-FR, NVD/CVE, OWASP, OpenCVE (alertes par produit).
  • Active : suivre les éditeurs et projets (blogs, releases), endoflife.date pour les fins de support, scorecards OpenSSF.
  • Cycle de vie d'une vuln : découverte → CVE/CVSS → mesures conservatoires (MCO/MCS : réduire la surface) → correctif → re-scan.
  • Le SBOM (partie 2) rend cette veille automatisable.
Le référentiel applicatif

OWASP

  • Top 10 : les catégories de risques les plus fréquentes (édition 2025 utilisée en partie 4).
  • Cheat Sheet Series : fiches pratiques par sujet (Password Storage, Session, JWT, Crypto…).
  • ASVS : exigences de sécurité vérifiables, par niveau (1 à 3).
  • WSTG : guide d'audit/pentest clé en main, avec sa checklist xlsx.
  • CWE (MITRE) : la « CVE de la programmation » : faiblesses de code que SonarQube/Semgrep savent détecter.
  • Outils : ZAP, Dependency-Track, Juice Shop, WebGoat, CycloneDX.
À retenir : Audit (WSTG) + DevSecOps (dépendances, code, config) + Veille (Top 10, fiches OWASP, CERT-FR). Les trois couvrent le cycle de vie complet.
Partie 2 · approche « blue team »

DevSecOps et sécurité de la supply chain

Intégrer la sécurité dans le SDLC et automatiser les vérifications dans le pipeline : retour rapide pour les devs avant les opérations coûteuses, et portes (gates) avant le déploiement.

Le pipeline du lab (GitLab CI)

buildbuild-appnpm ci, sans scripts ni Cypress
testunit-testtests unitaires
sast / scanpm audit · osv-scanner · SonarClouddépendances + code (CWE)

packagedocker-buildmulti-stage, non-root, push par digest

Familles d'analyse

SAST, SCA, IaC, DAST

  • SAST (code) : SonarQube/SonarCloud, Semgrep → CWE, qualité, syntaxes d'injection, appels fichiers.
  • SCA (dépendances) : npm audit, OSV-Scanner, Snyk, Trivy, Grype → CVE. Les résultats divergent (bases, périmètre système ou non) : comparer, puis choisir une référence.
  • IaC / config : hadolint, Trivy config, KICS → Dockerfile, Compose, Ansible, Terraform, secrets en clair.
  • DAST (appli qui tourne) : OWASP ZAP, WPScan → « pentest automatisé », voir partie 3.
Décomposition

SBOM

  • Inventaire des composants (CycloneDX / SPDX) généré à la fin du build : « décomposition prête à l'analyse ».
  • Scanner le SBOM de l'image finale élimine le bruit (devDependencies, éléments absents du runtime) par rapport au scan des sources.
  • Archiver le SBOM comme artefact long terme et le re-scanner périodiquement : cron + Grype, ou plateforme (Dependency-Track, Snyk).
  • Permet de répondre en minutes à « sommes-nous exposés à la CVE X ? ».
Supply chain ≠ CI/CD

Provenance et intégrité

  • Question centrale : ce que je télécharge est-il bien ce que l'éditeur a publié ? (cas Trivy début 2026).
  • Épingler par digest : node:24-trixie-slim@sha256:…, jamais un tag seul.
  • Vérifier les binaires : slsa-verifier, signatures Sigstore des outils.
  • Vérifier les paquets : npm audit signatures, Gradle --write-verification-metadata sha256, checksums Maven.
  • OpenSSF : Sigstore (cosign), SLSA, Scorecard et badges Best Practices pour choisir ses dépendances.
Signer ce que l'on produit

cosign, attestations, SLSA

  • Signature keyless : certificat éphémère lié à l'identité OIDC du pipeline, journal public Rekor.
  • Une substitution d'image est détectée à la vérification (no signatures found).
  • Attestation = signature d'un prédicat : SBOM, provenance SLSA v1 (qui a construit, depuis quelle source, quelle branche, quel déclencheur).
  • La politique (Rego) refuse une image construite hors de main ou par un trigger non autorisé.
Secrets

Vault

  • Place transverse : secrets du pipeline, de l'appli, clés de chiffrement, certificats, tokens courts.
  • Jamais de secret dans le dépôt ni dans l'image ; variables CI protégées et masquées, mais « masqué » ≠ sûr (fuite possible via encodage).
  • Rotation, audit des accès, identités de workload (OIDC) plutôt que clés statiques.
Registry privé

Nexus / Harbor en proxy

  • Un seul point d'entrée pour npm, Maven, PyPI, Docker Hub : cache, disponibilité, et quarantaine (délai, analyse, validation) avant mise à disposition.
  • Politique d'autorisation des paquets (licences, âge minimum, score).
  • Images de base internes durcies et re-scannées.
Durcissement

Image & conteneur

  • Multi-stage, copier uniquement le nécessaire, npm ci --omit=dev --ignore-scripts.
  • Utilisateur non-root en numérique (USER 1000:1000), distroless quand possible.
  • Pas de latest, .dockerignore, pas de secret en ARG/ENV.
Attaque sur le pipeline

Poisoned Pipeline Execution

  • Un contributeur modifie .gitlab-ci.yml (ou un script appelé) pour exfiltrer des secrets ou signer une image malveillante.
  • Parades : branches protégées, CODEOWNERS sur les fichiers CI, variables protégées limitées aux branches protégées, pas de secrets pour les MR issues de forks, runners dédiés, revue obligatoire.
  • La signature keyless ne « ment pas » : le certificat porte la branche et le pipeline d'origine, d'où l'intérêt de la politique de vérification.
Règle d'or des gates : fail fast pour les devs (lint, SAST, SCA sur les sources en quelques secondes), fail closed avant déploiement (scan d'image, signature, vérification de provenance). Un job en allow_failure + rapport HTML est un bon premier pas ; une vraie porte bloque.
Partie 3 · côté « red team »

Audit, pentest, DAST

Audit (WSTG) → Pentest → DAST : plus on automatise, plus on peut intégrer au pipeline ou aux routines de scan continu.

Démarche vue en TP (Vulnversity)

  • Reconnaissance : nmap, dirb/gobuster, exploit-db.
  • Exploitation : upload d'un fichier .phtml non filtré → reverse shell → écoute nc -lvnp 4444.
  • Post-exploitation : logs, fichiers users, clé SSH, GTFOBins → élévation de privilèges.
  • Chaque étape correspond à une défense de la partie 4 (filtrage upload, droits d'exécution, non-root, journalisation).

Environnement & outils

  • Kali (local, VM ou distante) + VPN vers la cible ; Burp Suite, sqlmap, hydra, nmap, ZAP.
  • Cyber Kill Chain, red team vs blue team, purple team.
  • WSTG : checklist xlsx comme trame de rapport (statut, criticité, actions, défauts relevés).

Apprendre et s'entraîner

  • OWASP Juice Shop, DVWA, WebGoat (leçons par item du Top 10).
  • TryHackMe – Jr Penetration Tester, CTF.
  • Bug bounty comme complément aux pentests contractuels.

DAST en continu

  • ZAP baseline/full scan sur un environnement de recette, à chaque release ou en nocturne.
  • Scanners spécialisés (WPScan pour WordPress, Nuclei pour des templates de vulnérabilités).
  • Complète le SAST : détecte les erreurs de configuration et de logique visibles seulement à l'exécution.
Partie 4 · à promouvoir aux devs

Bonnes pratiques × OWASP Top 10 (2025)

Pour chaque catégorie : ce que ça couvre, les pratiques à adopter côté application, et la Cheat Sheet OWASP de référence. Les étiquettes indiquent où l'automatisation du pipeline aide et ce qui relève du système.

A01Broken Access Controlinchangé depuis 2021

Le risque

  • IDOR : /api/orders/1234 accessible sans vérifier le propriétaire.
  • Élévation (user → admin), contournement par URL, méthodes HTTP non filtrées, CORS permissif.
  • Fichiers « privés » servis publiquement, robots.txt qui révèle les chemins sensibles.

À promouvoir

  • Deny by default, contrôle côté serveur sur chaque requête ; le front ne fait que masquer.
  • RBAC / ABAC centralisé (middleware, policies), vérification de propriété sur chaque ressource.
  • Identifiants non devinables (UUID) mais ce n'est pas une protection en soi.
  • CORS en liste blanche d'origines, pas de * avec credentials.
  • Rate limiting par utilisateur ; journaliser les refus d'accès.
tests d'autorisation autoDAST / ZAP

Cheat Sheets : Authorization, Access Control, IDOR Prevention, CORS.

A02Security Misconfiguration2021 : A05

Le risque

  • Comptes/mots de passe par défaut, debug activé en prod, stack traces exposées.
  • En-têtes HTTP manquants, listing de répertoires, services inutiles ouverts.
  • Conteneur root, secrets en variables d'environnement commités.

À promouvoir

  • En-têtes : Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options: nosniff, Referrer-Policy, Permissions-Policy.
  • Configuration par environnement, identique en structure (IaC), secrets injectés depuis un vault.
  • Désactiver debug, pages d'erreur par défaut, endpoints d'admin exposés.
  • Images minimales, non-root, ports et capacités réduits.
KICS · trivy config · hadolintdurcissement OS / WAF

Cheat Sheets : HTTP Headers, Docker Security, Infrastructure as Code Security, Secrets Management.

A03Software Supply Chain Failures2021 : A06 Vulnerable & Outdated Components (élargi)

Le risque

  • Dépendances vulnérables ou abandonnées, paquets malveillants (typosquatting, maintainer compromis).
  • Outils de build ou images de base substitués, pipeline empoisonné.

À promouvoir

  • Lockfile commité, npm ci, --ignore-scripts en CI ; mises à jour automatisées (Renovate/Dependabot) avec revue.
  • SCA à chaque pipeline, SBOM archivé et re-scanné, Dependency-Track.
  • Images et actions/outils épinglés par digest ; vérification de signature/provenance (cosign, slsa-verifier, npm audit signatures).
  • Registry proxy interne avec quarantaine ; choisir ses libs via OpenSSF Scorecard et endoflife.date.
  • Signer et attester ce que l'on livre (cosign + SLSA).
osv · trivy · grype · syft · cosignNexus / Harbor

Cheat Sheets : Software Supply Chain Security, Vulnerable Dependency Management, CI/CD Security, NPM Security.

A04Cryptographic Failures2021 : A02

Le risque

  • Mots de passe en MD5/SHA-1 ou sans sel, données personnelles en clair en base ou dans les sauvegardes.
  • TLS absent ou mal configuré, clés dans le code, algorithmes maison.

À promouvoir

  • Mots de passe : Argon2id (salt unique par utilisateur, pepper hors base), repli scrypt/bcrypt ; jamais de chiffrement réversible pour les mots de passe.
  • TLS 1.2+/1.3 partout, y compris appli ↔ base en cloud ; HSTS.
  • Stratégie : data-at-rest (disque/TDE) contre le vol de support, chiffrement par champ (AES-256-GCM) contre la fuite SQL, clés dans un vault/KMS avec rotation.
  • Pour les données les plus sensibles : clé dérivée du secret de l'utilisateur (voir focus 4b).
  • Sauvegardes chiffrées, clé absente du support de stockage ; données masquées en dev/preprod.
Semgrep / Sonar (algos faibles)jamais de crypto maison

Cheat Sheets : Password Storage, Cryptographic Storage, Key Management, TLS, Transport Layer Security.

A05Injection2021 : A03 (inclut XSS)

Le risque

  • SQL, NoSQL, commandes système, LDAP, templates, XSS (réfléchi, stocké, DOM).
  • Outils d'attaque : sqlmap, payloads XSS, injection dans les uploads (partie 3).

À promouvoir

  • Requêtes paramétrées / ORM (PDO préparé plutôt que concaténation), jamais de SQL dynamique à partir d'une entrée.
  • Never trust user input : validation en liste blanche côté serveur (le front n'est qu'un confort).
  • Encodage de sortie contextuel (HTML, attribut, JS, URL) ; frameworks qui échappent par défaut ; CSP comme filet.
  • Pas d'appel shell avec des entrées ; API natives plutôt que exec.
  • Chemins de fichiers normalisés et bornés (path traversal).
Sonar · Semgrep (CWE-89, 79, 78)ZAPWAF

Cheat Sheets : Injection Prevention, SQL Injection Prevention, Query Parameterization, XSS Prevention, Input Validation, OS Command Injection Defense.

A06Insecure Design2021 : A04

Le risque

  • Défaut de conception que le code parfait ne corrige pas : logique métier abusable, absence de limites, récupération de compte faible.

À promouvoir

  • Threat modeling léger dès la conception (STRIDE, cas d'abus), exigences ASVS dans les user stories.
  • Limites métier : quotas, anti-automatisation (rate limit, CAPTCHA en sachant qu'il se contourne), étapes de validation.
  • Séparation des environnements et des privilèges, principe du moindre privilège.
  • Revue de sécurité des flux sensibles (paiement, reset de mot de passe, upload).
revue de conceptionASVS

Cheat Sheets : Threat Modeling, Secure Product Design, Abuse Case, Attack Surface Analysis.

A07Authentication Failures2021 : A07 Identification & Authentication Failures

Le risque

  • Brute force, credential stuffing, messages d'erreur qui révèlent l'existence d'un compte.
  • Sessions qui n'expirent pas, tokens dans localStorage, fixation de session.

À promouvoir

  • MFA : TOTP ou mieux passkeys / WebAuthn (résistants au phishing) ; SMS en dernier recours.
  • Déléguer : OAuth 2.0 / OpenID Connect avec PKCE, SSO ; ne pas réécrire l'authentification.
  • Message d'échec générique (« identifiants invalides »), même temps de réponse ; idem pour la réinitialisation.
  • Rate limiting, verrouillage progressif, détection de mots de passe compromis (HIBP), politique de longueur plutôt que de complexité.
  • Session : régénérer l'ID à la connexion, expiration, invalidation à la déconnexion.
  • JWT → cookie HttpOnly; Secure; SameSite=Lax|Strict, pas en localStorage ; voir focus 4b.
ZAP auth testsfail2ban · CrowdSec · WAF

Cheat Sheets : Authentication, Session Management, Multifactor Authentication, Forgot Password, Credential Stuffing Prevention, JSON Web Token.

A08Software or Data Integrity Failures2021 : A08

Le risque

  • Code ou données acceptés sans vérification d'intégrité : désérialisation d'objets non fiables, mises à jour non signées, scripts tiers modifiés.

À promouvoir

  • Subresource Integrity pour les scripts CDN, CSP.
  • Ne jamais désérialiser des données non fiables en objets (préférer JSON + schéma validé).
  • Signer les artefacts et les mises à jour, vérifier avant exécution ; JWT : vérifier alg, iss, aud, exp, refuser none.
  • Intégrité du pipeline (branches protégées, revue, CODEOWNERS) : recoupe A03.
cosign verify · policy

Cheat Sheets : Deserialization, Third Party JavaScript Management, Software Supply Chain Security.

A09Security Logging & Alerting Failures2021 : A09 Logging & Monitoring

Le risque

  • Intrusion détectée des mois plus tard ; logs absents, non centralisés, ou contenant des secrets.

À promouvoir

  • Journaliser les événements de sécurité : connexions (succès/échecs), changements de droits, accès refusés, validations rejetées, actions admin.
  • Logs structurés (JSON), horodatés (NTP), avec identifiant de corrélation ; jamais de mot de passe, token, carte bancaire, données personnelles brutes.
  • Centralisation (ELK/Loki, SIEM) et alertes réellement traitées (SOC) ; conservation adaptée au RGPD.
  • Protéger les logs contre l'injection et la modification.
SIEM · SOC

Cheat Sheets : Logging, Logging Vocabulary, Application Logging Vocabulary.

A10Mishandling of Exceptional Conditionsnouveau en 2025

Le risque

  • Erreurs mal gérées : exception avalée, état incohérent, « fail open » (le contrôle échoue → accès accordé), stack trace au client, épuisement de ressources.

À promouvoir

  • Fail closed : en cas d'erreur d'un contrôle de sécurité, refuser.
  • Gestion centralisée des exceptions : réponse générique à l'utilisateur, détail dans les logs.
  • Timeouts, retries bornés, limites de taille (body, upload), circuit breakers.
  • Tests des cas limites et des chemins d'erreur, pas seulement du chemin nominal.
tests · Sonar (exceptions vides)

Focus 4b

Hash, chiffrement, tokens : les choix concrets

Les quatre sujets qui reviennent dans chaque revue de code, avec les paramètres recommandés aujourd'hui.

Mots de passe

Argon2id, salt et pepper

  • Argon2id : m = 19 MiB, t = 2, p = 1 (minimum OWASP) ; ajuster pour ~0,5 s côté serveur. Repli : scrypt, puis bcrypt (coût ≥ 10, limite 72 octets).
  • Salt : aléatoire, unique par utilisateur, stocké avec le hash (les libs le font).
  • Pepper : secret global hors base (vault, variable d'env, HSM), appliqué via HMAC avant le hash ou en chiffrant le hash ; un dump SQL seul devient inutilisable.
  • Re-hasher à la connexion quand les paramètres évoluent.
hash = argon2id( hmac_sha256(pepper, password), salt )
Données

Stratégies de chiffrement

at rest
Disque / TDE de la base. Protège contre le vol de disque et de sauvegarde, pas contre une injection SQL : l'appli lit en clair.
par champ
Chiffrer depuis l'appli les colonnes sensibles (IBAN, santé, documents) en AES-256-GCM avec nonce unique. Perte de recherche/tri sur ces colonnes ; prévoir un hash d'index si besoin.
enveloppe
DEK par enregistrement ou par tenant, chiffrée par une KEK dans un KMS/Vault ; rotation sans re-chiffrer toute la base.
clé utilisateur
KEK dérivée du mot de passe (Argon2id) ou d'une passkey ; le serveur ne peut pas lire. Prix : perte du mot de passe = perte des données, prévoir une clé de récupération ; pas de traitement serveur possible.
backups
Dump logique ou backup physique, archive chiffrée, clé jamais présente sur le stockage hot/cold. Tester la restauration.
dev / preprod
Jamais de données réelles : jeu de test ou script de pseudonymisation à l'import.
Sessions & API

JWT, cookies, CSRF

  • Stocker le token dans un cookie HttpOnly; Secure; SameSite=Lax (ou Strict) : inaccessible au JS, donc à une XSS.
  • Cookie ⇒ protection CSRF : SameSite + token anti-CSRF ou en-tête custom sur les requêtes qui modifient l'état.
  • Access token court (minutes) + refresh token rotatif, révocable, lié à l'appareil.
  • Côté serveur : algorithme imposé (RS256/ES256/EdDSA), vérifier iss, aud, exp, nbf, kid ; refuser none et la confusion HS/RS.
  • Pas de données sensibles dans le payload (lisible en base64).
  • Session serveur classique (ID opaque) reste un très bon choix pour une appli web monolithique.
Identité

MFA, SSO, protocoles

  • Ordre de préférence : passkeys / FIDO2 → TOTP → push → SMS/e-mail.
  • MFA obligatoire pour les comptes admin et les actions sensibles (step-up).
  • OAuth 2.0 + OIDC avec PKCE (y compris pour les applis confidentielles), pas de flux implicite ni ROPC.
  • Codes de récupération à usage unique, hashés comme des mots de passe.
  • Permissions : RBAC pour les rôles, ACL/ABAC pour la propriété des ressources, cohérence front ⇄ back.
Côté système

Ce que l'infra ajoute

  • WAF / « cloud firewall » : Cloudflare, Sucuri, AWS/OVH/Azure ; on-prem : pfSense/OPNsense, Fortinet, Palo Alto ; open source : CrowdSec, Traefik + middlewares.
  • Anti brute force réseau : fail2ban, GeoIP, listes de blocage ; honeypots.
  • Permissions système : utilisateur dédié, pas de root, cloisonnement conteneur, répertoires d'upload sans exécution.
  • Ces mesures complètent le code, elles ne le remplacent pas.
Partie 5

Checklist à afficher au-dessus du bureau

La version courte, à relire à chaque revue de code et à chaque mise en production.

Dans le code

  • Contrôle d'accès serveur sur chaque route, deny by default
  • Requêtes paramétrées, zéro concaténation SQL
  • Validation liste blanche + encodage de sortie
  • Argon2id + salt + pepper hors base
  • Token en cookie HttpOnly/Secure/SameSite, CSRF géré
  • JWT : alg imposé, iss/aud/exp vérifiés
  • MFA disponible, obligatoire pour les admins
  • Messages d'erreur génériques, détails en log
  • Fail closed, timeouts, limites de taille
  • Upload : extension + MIME + taille, hors webroot, no exec
  • Champs sensibles chiffrés (AES-GCM), clés en vault
  • Pas de secret, de token ni de PII dans les logs
  • En-têtes CSP, HSTS, nosniff, Referrer-Policy
  • SRI sur les scripts tiers

Dans le pipeline

  • Lockfile commité, npm ci --ignore-scripts
  • SAST (Sonar/Semgrep) + SCA (OSV/Trivy) à chaque push
  • Scan IaC (KICS, Trivy config, hadolint)
  • Image multi-stage, non-root, base épinglée par digest
  • SBOM généré, archivé, re-scanné la nuit
  • Gate bloquante sur CRITICAL/HIGH avant déploiement
  • Image signée (cosign keyless) + attestations SBOM et SLSA
  • Vérification de signature et de politique au déploiement
  • Outils tiers vérifiés (slsa-verifier, signatures npm)
  • Branches protégées, CODEOWNERS sur la CI, variables protégées
  • Secrets depuis un vault, jamais dans le dépôt
  • Registry proxy interne avec quarantaine
  • DAST (ZAP) sur la recette avant release
  • Renovate/Dependabot + endoflife.date suivis
